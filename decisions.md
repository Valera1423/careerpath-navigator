## ADR-001: FastAPI как backend-фреймворк

**Дата:** 2026-08-15  
**Статус:** Принято

**Контекст.**  
MVP для хакатона, срок 2 недели. Нужен быстрый старт, автодокументация, Pydantic для валидации.

**Решение.**  
FastAPI + Pydantic v2 + SQLAlchemy 2.0.

**Альтернативы.**
- Django REST — тяжелее, много boilerplate
- Flask — нет автогенерации OpenAPI
- aiohttp — ниже уровень, больше рутины

**Последствия.**
✅ Автоматический Swagger/OpenAPI  
✅ Pydantic-валидация из коробки  
✅ Async-native (важно для httpx к «Работе России»)  
❌ Меньше готовых admin-панелей (пришлось не нуждаться)

## ADR-002: PostgreSQL как основная БД

**Дата:** 2026-08-16  
**Статус:** Принято

**Контекст.**  
Нужна БД для профиля, плана, откликов, симулятора, Employer API. MVP, но с планом на production.

**Решение.**  
PostgreSQL 16 (Neon на бесплатном тарифе). SQLAlchemy 2.0 + psycopg[binary] (sync).

**Альтернативы.**
- SQLite — просто, но не работает на serverless/Wispbyte (read-only FS)
- MongoDB — нет смысла, схема реляционная
- MySQL — меньше поддержки в Python-экосистеме

**Последствия.**
✅ Транзакции, JSON-поля, полнотекстовый поиск  
✅ Free-tier Neon достаточен для MVP  
✅ Легко переехать на любой managed PG  
❌ Network overhead vs SQLite при локальной разработке (митигируется dev-fallback на SQLite)

## ADR-003: Синхронный SQLAlchemy вместо async

**Дата:** 2026-08-16  
**Статус:** Принято

**Контекст.**  
FastAPI поддерживает async. Можно было писать `create_async_engine` + `AsyncSession`.

**Решение.**  
Sync SQLAlchemy + sync роутеры (FastAPI оборачивает их в threadpool).

**Альтернативы.**
- Async ORM (asyncpg) — сложнее, нужен везде await, миграции через alembic async
- Tortoise ORM — менее зрелый
- Raw SQL — быстро, но много boilerplate

**Последствия.**
✅ Проще код, легче для новичков  
✅ Не блокирует event loop (FastAPI использует threadpool)  
✅ Alembic в sync-режиме — стандартный  
❌ При большом RPS будет хуже, чем async, но у нас не тот случай  
❌ Один из последних зависимостей — `asyncpg` — можно удалить

## ADR-004: React + TypeScript + Vite

**Дата:** 2026-08-17  
**Статус:** Принято

**Контекст.**  
Frontend для Mini App в MAX. Нужна типизация, быстрый dev-сервер, сборка.

**Решение.**  
React 18 + TypeScript 5 + Vite 5. Zustand для точечного state — не понадобился, используем hooks.

**Альтернативы.**
- Next.js — SSR не нужен для Mini App
- Vue — команда знает React
- Svelte — меньше экосистема

**Последствия.**
✅ Vite — мгновенный HMR, быстрая сборка  
✅ TS ловит ошибки до деплоя  
✅ React-экосистема (recharts, xstate, react-i18next)  
❌ npm-зависимостей много (~250)

## ADR-005: MAX UI через адаптер

**Дата:** 2026-08-18  
**Статус:** Принято

**Контекст.**  
Библиотека `@dementevdev/max-ui` молодая, API может меняться. Нужна изоляция.

**Решение.**  
Единственный файл `src/ui/index.tsx`, который импортирует из MAX UI. Все компоненты — через него.

**Альтернативы.**
- Прямой импорт везде — сломает 20+ файлов при обновлении библиотеки
- Своя UI-библиотека — долго, противоречит ТЗ

**Последствия.**
✅ Смена версии MAX UI — правка одного файла  
✅ Fallback на нативные HTML-элементы, если компонента нет  
✅ Легко тестировать  
❌ Чуть больше кода-обёртки

## ADR-006: XState для симулятора

**Дата:** 2026-08-20  
**Статус:** Принято

**Контекст.**  
Симулятор дня — это конечный автомат: узлы сценария, переходы по выбору, финальное состояние. Нужно предотвратить невалидные состояния.

**Решение.**  
XState v5 + `@xstate/react` для симулятора. Остальные экраны — обычные hooks.

**Альтернативы.**
- Redux Toolkit — оверкилл для одного экрана
- useState — не защищает от невалидных переходов
- Zustand — не про state machines

**Последствия.**
✅ Невалидные состояния невозможны by design  
✅ Визуализация автомата через stately.ai  
✅ Легко тестировать (переходы — чистые)  
❌ Дополнительная зависимость

## ADR-007: Словарь навыков в YAML

**Дата:** 2026-08-19  
**Статус:** Принято

**Контекст.**  
Паттернов навыков — 100+. Они будут пополняться без изменения логики.

**Решение.**  
`app/data/skills.yaml` + `roles.yaml`. Загрузка через `importlib.resources` с `lru_cache`.

**Альтернативы.**
- Словарь в Python — при правке нужно перезапускать сервис, диffы шумные
- БД — оверкилл, словарь статический
- JSON — менее читаем для людей

**Последствия.**
✅ Правка без кода — маркетинг/HR может пополнять  
✅ `lru_cache` — загрузка раз за процесс  
✅ Легко ревьюить diff  
❌ Не подходит для динамического обновления (обновляется при рестарте)

## ADR-008: Webhook вместо long polling для бота

**Дата:** 2026-09-01  
**Статус:** Принято

**Контекст.**  
MAX Bot API поддерживает и webhook, и long polling. Документация MAX явно указывает: long polling «не подходит для production».

**Решение.**  
Webhook endpoint `/webhook/max` на FastAPI. Подписка через `POST /subscriptions`.

**Альтернативы.**
- Long polling — запрещён в production MAX, ограничен по скорости и сроку хранения
- Гибридный режим — избыточно

**Последствия.**
✅ Соответствие требованиям MAX  
✅ Масштабируемо  
✅ Мгновенная доставка  
❌ Требует HTTPS на 443 с валидным сертификатом  
❌ Нужно хранить `MAX_WEBHOOK_SECRET`

## ADR-009: Сертификаты Минцифры через бандл

**Дата:** 2026-09-25  
**Статус:** Принято

**Контекст.**  
MAX API использует сертификаты НУЦ Минцифры. На чистом Python-образе их нет → `CERTIFICATE_VERIFY_FAILED`.

**Решение.**  
`run_both.py` скачивает бандл `russiantrustedca.pem` с `gu-st.ru` при первом запуске. Сохраняет в `/home/container/russian_trusted.pem`. `max_api.py` подгружает его в `ssl.SSLContext` через `load_verify_locations`.

**Альтернативы.**
- `verify=False` — небезопасно, MITM
- Установка сертификата в образ — сложнее обновлять
- Свой CA в коде — плохая практика

**Последствия.**
✅ Автоматическая установка, работает на любом хостинге  
✅ Сертификаты можно обновлять — просто удалить файл  
❌ Первый запуск требует интернет к `gu-st.ru`  
❌ Хардкод пути `/home/container/` — работает на Wispbyte/Pterodactyl, для Docker нужен другой путь

## ADR-010: Employer API с анонимизацией

**Дата:** 2026-09-20  
**Статус:** Принято

**Контекст.**  
Идея «инфраструктурный слой» для конкурса. Нужно дать HR доступ к студентам, не нарушая 152-ФЗ.

**Решение.**  
Отдельный API `/employer/v1/`. Доступ по API-ключу (bcrypt hash в БД). Возвращает только анонимизированные данные: без ФИО, email, точного ID. Регион округляется до федерального округа. Работает только при `employer_opt_in = true`.

**Альтернативы.**
- Прямой доступ к БД — нарушает 152-ФЗ
- Публичный API без ключей — DDoS, утечки
- OAuth — избыточно для MVP

**Последствия.**
✅ Соответствие 152-ФЗ  
✅ Понятный контракт для интеграций  
✅ Путь к монетизации (B2B)  
❌ Требует модерации работодателей (сейчас — через `X-Admin-Secret`)

## ADR-011: Fallback-данные для внешних API

**Дата:** 2026-08-21  
**Статус:** Принято

**Контекст.**  
«Работа России» может быть недоступна. Жюри/инвесторы должны увидеть работающее демо в любых условиях.

**Решение.**  
Fallback-набор `FALLBACK_VACANCIES` в `trudvsem.py`. Флаг `source: "fallback"` в ответе. UI показывает жёлтое уведомление.

**Альтернативы.**
- Просто 503 — плохое демо
- Только кэш — не работает на пустом старте
- Дублировать в БД — сложнее поддерживать

**Последствия.**
✅ Демо всегда работает  
✅ Прозрачно для пользователя  
❌ Риск, что fallback замаскирует реальную проблему API

## ADR-012: Один контейнер для backend и планировщика на Wispbyte

**Дата:** 2026-09-26  
**Статус:** Принято (для Wispbyte)

**Контекст.**  
Wispbyte (бесплатный тариф) даёт один контейнер. Нужны и uvicorn, и планировщик напоминаний.

**Решение.**  
`run_both.py` запускает APScheduler в фоновом потоке + uvicorn в главном. На Vercel/Railway можно разделить, но здесь — совмещены.

**Альтернативы.**
- Отдельный воркер — платно на Wispbyte
- Cron — нет гарантий, зависит от панели
- Отказ от планировщика — потеря фичи

**Последствия.**
✅ Один контейнер — минимальные ресурсы  
✅ Оба процесса живы, пока uvicorn работает  
❌ Планировщик умирает при падении uvicorn (для MVP — приемлемо)
